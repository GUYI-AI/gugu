# Local password vault storage and encrypted audit

These desktop-main primitives are dormant. Nothing registers them in IPC, MCP, device actions, the server, diagnostics or transcript upload. They do not enable password saving or use. Integration must supply the real native-file boundary, permission/readiness checks, trusted local person authentication and browser coordinator; test doubles cannot supply production readiness.

The native factory uses `createVaultStorage(dependencies, browser, acquireFeatureGuard)` from `host.ts`. Dependencies are `VaultStorageDependencies` (the existing `VaultDependencies` without browser/readiness); supply `macVaultKeyProtector()` as keys, the startup-protected root and actual trusted identity/lifecycle adapters. The browser argument is the fixed `VaultBrowserSink`. The final argument is the bound ready-only adapter to the real `PasswordFeatureReadiness.check`; translate unavailable into `VaultError('UNAVAILABLE')`, with no default allow. Host methods and key-protector methods are captured once. The result is a frozen `{ vault, outcomeAudit }`, where the audit port is exactly `vault.outcomeAudit`, not another writer or lock lifecycle.

Full handback integration constructs its unique registry with that audit port, fixed surface and all six actual output custodians. Its cleanup/settle closures are the same fixed browser sink passed to storage. Storage clears its buffers before cleanup/post-use audit/settle; this does not establish the custodians' real writer drain or absence of console/network/capture/temporary/crash/error artifacts. The approved Beta path instead uses the shared build-channel gate and original per-use approval authority: the entry is visible in Beta builds and hidden in stable builds, with no account allowlist or runtime/request override. Deferred custodians/acceptance are not reported as ready. It still provides no Agent plaintext export or password logging. The factory also owns lifecycle installation and must await disposal before replacing the account's service; construction does not register a person or Agent entrypoint.

The fixed host obtains the actual vault installation source from `await vault.prepareInstallationIdentity()`. It returns a `LivePasswordFact` with `value: { installationId, status: 'pending_setup' | 'persisted' }`, actual lifecycle generation, revocation signal and a synchronous assertion. It does not write files, create directories or generate keys/recovery material. With an empty protected root, storage reserves one UUID; initialization later persists exactly that UUID only under its save guard. It is not installationBinding. A pending fact may qualify save; use requires a freshly read persisted fact plus the other use checks. The pending fact remains conservatively pending across its own successful save, so setup's same guard can finish without upgrading that old fact into use evidence. Lock/dispose revokes old facts; replacing/removing an observed manifest invalidates that installation source. Reader preparation does not re-enter the serial writer queue, so a real readiness reader can call it during first setup without deadlock.

Settings must use `await vault.isInitialized(person)` for the account's setup state. A persisted installation manifest is insufficient: setup writes it before local verification and recovery confirmation. This person-only, read-only method validates the protected account document without decrypting credentials, prompting, generating keys or writing files. Cancelled verification and unconfirmed recovery remain uninitialized; a completed locked vault remains initialized. Missing recorded account data and damaged metadata remain explicit failures rather than an empty replacement.

## Storage and keys

Use the startup-registered `GUGU_HOME/private/password-vault/v1/` root. The host must obtain that exact root and its current protection status from the native-file exclusion registry before constructing this service. Every filesystem operation checks protection again, including before creating directories. No recovery export, backup, shared-folder copy or alternate storage location is created.

An installation manifest binds a random installation id to the host's stable local installation binding. Each account has a separate hashed directory, independent random 256-bit data key and credential file. Credential records and their management-operation ledger use Node/OpenSSL AES-256-GCM with a fresh 96-bit nonce and a 128-bit authentication tag. Authenticated context binds format, account, installation, vault and purpose. Metadata in the credential payload is encrypted too. Private audit bodies use the same data key with separate authenticated context; no audit key/unlock state is cached separately. Filesystem names, sizes and timestamps are not a tamper-proof or metadata-hiding format.

The desktop adapter wraps the data key through Electron safeStorage (macOS Keychain). Setup, unlock and recovery require local system verification before key access. The current adapter uses Touch ID and refuses operation when Touch ID, the Keychain or the real macOS Electron main process is unavailable. A cloud login or an Agent-supplied person assertion is insufficient. Integrating the trusted person context remains the host's responsibility.

Recovery setup generates 256 random bits and requires confirmation in the trusted local form. The material independently wraps the data key; it is not written to a plaintext file or exposed as an Agent operation. Recovery requires the retained encrypted installation data. Losing both material and an installation that can unlock makes old credentials unrecoverable; material cannot recreate missing data. Recovery rewraps the existing authenticated data key with the current system protector. There is no cloud recovery or cross-device importer. Missing, damaged or wrongly bound data is an explicit failure, never an empty replacement.

Writes use exclusive temporary files, file fsync, atomic rename and directory fsync, inside the protected root. Symlinked directories and symlinked/multiply-linked private files are refused. These checks supplement the independent native-file exclusion; they do not replace it or promise protection against arbitrary native programs. There is one active service/writer for a root in desktop main.

## Locking, management and trusted use

`LocalPasswordVault` has one key/lock lifecycle and an unrepeatable UUID epoch. Restart starts locked. Lock synchronously changes the epoch, removes reachable plaintext copies and zeroes mutable key/secret buffers before waiting for audit I/O or browser cleanup. `installVaultLifecycle` binds OS lock, suspend, account changes, logout and app exit when installed by the host. It never unlocks on resume.

Only a host-authenticated local person may list, set up, confirm recovery, unlock, recover, save, edit, delete, read audit or clear audit. Lists contain opaque id/version/epoch references, exact origins and a recognizable masked account. The single `maskedAccount` function retains the first character and a validated email domain, or the first character plus `***` for other accounts. A one-grapheme account or email local part is completely hidden; malformed/control-bearing text cannot expose a domain-shaped remainder. Save summaries use the same function, including retries, without a new plaintext export. Save/edit/delete take a stable management operation UUID. An encrypted pending/committed ledger binds that id to its original request with keyed HMAC; lost responses, restarts and post-commit audit failures can retry the original operation without creating a second effect. A changed request cannot reuse the id.

Edits/deletion synchronously revoke the affected reference and abort its active buffers, then wait for cleanup before completion. Subsequent fresh reference checks verify account context, version and epoch; invalidation notifications are not the sole check. Locking/deletion never claims website logout.

Setup/save/use require the constructor-captured `acquireFeatureGuard(save | use, signal)` adapter. Its type reuses the permission module's live `PasswordAvailability` ready guard. A missing adapter, void result, boolean assertion or asynchronous `assertCurrent` refuses operation; the old void readiness callback grants nothing. Setup retains one guard across recovery generation and confirmation. Save/use retain their guard across waits, recheck before each actual filesystem mutation and plaintext delivery/submission, and propagate revocation to clear pending recovery keys, management fields and active secret buffers. Late successful fill/cleanup/audit/settlement results cannot restore qualification; withdrawal after a possible effect returns uncertainty and retains isolation. This qualification grants no person identity, approval or submission right and adds no second vault lock state. Closing an operation releases its guard; lock also cancels pending acquisition, so a late result cannot revive it.

The claimed Authority lease supplies two distinct signals. `signal` stops filling and submission, including during normal proof-only cleanup. The mandatory `revokedSignal` is the original approval revocation signal also registered with the handback lifecycle. Continuing feature qualification combines only that signal with the vault epoch and real readiness; normal cleanup does not invalidate it. A missing, malformed or already aborted revocation signal refuses use before preparing buffers. Genuine readiness/approval/lock revocation still clears buffers and prevents a late success from qualifying.

An already issued write cannot be rolled back by revoking its guard. If revocation interrupts a save after a write starts, storage drops its cached key and reports failure; it neither rolls back nor retries automatically. The trusted person must inspect the durable state after unlocking and explicitly resume with the original management operation id if appropriate. Required failure cleanup and terminal outcome audit remain available after qualification fails; they cannot fill, submit or hand back a surface.

`useCredential` accepts the browser coordinator's process-local capability and shared `CredentialUseBinding`. It claims once, checks account/installation/version/epoch/origin, obtains a reliable pre-use audit receipt and calls only the sink fixed at host construction. There is no per-call secret receiver or secret-return API. The sink must check actual fields/form/frame/origin atomically with each fill and submission, call the supplied fresh checks at both steps, obtain a new pre-submission audit receipt with `prepareSubmission()` after fill, and claim the sole submission. Without that receipt the synchronous submission claim refuses, including an audit outage between fill and submit. Buffers are cleared on every result. These primitives do not implement the real browser checks or isolated-login boundaries.

`cleanup(useId)` only proves clearing and always retains the isolated login surface. A `cleaned` result cannot hand back the surface/session. Only the browser coordinator may finalize handoff after the same use's required audit is recorded, all cleanup evidence is valid and the result is not uncertain. Audit failure, possible effects and unconfirmed cleanup cannot be cleared by timeout, finally blocks or a late success. The bound private `loginSurfaceId` is never an Agent result.

The fixed sink must implement `settle(event)`. For every successfully claimed terminal path, storage clears buffers, attempts cleanup and required post-use audit, then notifies that sink with the original capability, captured binding, outcome, effect possibility and actual audit result. Unclaimed capabilities trigger no cleanup or settlement. A settlement failure returns a retained/uncertain or unavailable result. No private person view crosses this adapter.

`outcomeAudit` is one fixed host-only port for the handback coordinator. It issues a process-local proof only from its own successful durable write closure, for an already claimed context. `matches(recorded, expected)` verifies proof identity, both receipt IDs, the original capability and every binding/outcome field against the issuer's snapshot and the same vault lifecycle. Serialized/cloned proofs, changed receipt IDs and stale references do not qualify. A changed outcome after person interaction requires a new `appendOutcome` event/proof. Lock, audit clear and credential invalidation make old evidence unusable. Proofs contain no keys or credentials, are not persisted, and grant no approval, submission or handback authority.

JavaScript strings and OS/website copies cannot be forensically zeroed. The implementation clears mutable buffers and drops reachable feature-owned plaintext fields; it does not claim secure erasure of V8 heaps, filesystem backups or a compromised local account.

## Audit and failures

`appendAudit(event, { effectPossible })` accepts only a strict structured schema with a stable event UUID, actual actor/session, credential reference/version, exact HTTPS origin, request/use ids, action/decision/source and outcome. It accepts no arbitrary notes, password, page/form/console body, query or raw error. Repeating the same event id is idempotent; changed-event reuse is rejected. Internal management transitions use stable receipts across retries.

Records are encrypted individually and retained for 90 days by default. Only the trusted person can decrypt/read or clear them. There is no general-permission JSONL mirror and no plaintext fallback. Reliable receipts follow durable writes. Before-effect audit failure blocks the sink. After a possible effect, failure returns uncertainty with no retry and the isolated login surface retained. Lock itself cannot wait to revoke secrets because an audit write failed. Public failures carry fixed codes, never lower-layer messages/causes. The service's JSON representation contains only a generic health state; private runtime fields are not enumerable.

## Verification boundaries

The unit suites exercise real temporary filesystem persistence and OpenSSL encryption with synthetic person/key/browser authorities, including recovery/corruption, account isolation, operation/event replay, retention, lock/edit races, live qualification revocation during awaits, and before/after-effect audit failures. They include a composed permission-readiness guard and assert actual zero filesystem mutations/secret deliveries after withdrawal before an effect, plus a committed-rename case that verifies no rollback or automatic retry. They are not proof of trusted person UI, native-file gateway coverage, actual HTTPS submission/login-surface isolation or external transcript/diagnostic safety. Those release paths remain disabled until integrated, tested with disposable canaries and independently reviewed.
