# 客户端状态模型

> 代码里用 `@@@client-state-model` 指到这份文档。清点表里的「PR n」是客户端状态迁移这一组 PR 的序号：PR 1 是 #2685，PR 2 是引入本文档的那个 PR。

先按「真值归谁」把状态分成四类，每类、每种形状只用一种机制。服务端的键值状态统一叫 **replica**（现名 readModel）。组件读任何状态都只用一个订阅原语 `useSelect`，见第 6 节。

## 1. 四类和判定

**判定只问一个问题：真值归谁？**

| 真值归 | 类 | 机制（每种形状一种） |
|---|---|---|
| 账号、服务端、别的机器 | ① 服务端状态 | **键值** → `replica`。**有序区间 / 流** → 各自的流引擎：消息 = IM 消息存储；会话流、终端输出 = 会话宿主流；消息预览 = 云端预览广播流。**协同文档** → CRDT（hocuspocus）。 |
| 这台设备的主进程，没有推送竞争 | ② 本机偏好 | `appSettings` 键；渲染层通过 replica 的 device 作用域只读 |
| 这个界面 | ③ 视图状态 | 视图状态：草稿、滚动、tab、展开状态。编辑器文档是草稿的「活」形态，存储里的那份是它的落盘。现在落盘有 `rpc.viewState.save` 和 localStorage 草稿；连续性报告 R2 提的「按（会话, 面板）做键的视图状态表」还没建，等它建好以后，这一类只用那张表 |
| 这次交互 | ④ 瞬时状态 | 只一个组件用：`useState`。跨组件用（弹窗栈、提示、上传进度、导航、命令注册、各个 Bridge）：模块级 `createSelectStore` |

**补充规则：**
- **环境事实**（登录态、可达性、系统权限、前后台）属于 ①，形状是键值，推送档位是「信号」。登录态是生命周期的根，归会话发布（`observeRendererSession`）。
- **派生值只算不存**：会话列表投影、未读总数、角标。
- **一份数据横跨两类时，拆开分别归类**：
  - 读位、发送中的消息、会话输入：服务端的数据（①）经 **发件箱** 写入，不回滚。
  - `unread_locator` 是 ① 的数据，据它决定滚到哪里，属于 ③。

## 2. replica 的三个入口和不丢更新

**版本域。** 每个模型都要声明两件事：

- **版本域**，选一种：
  - 账号修订号
  - 服务端 head：读取接口返回读到的修订位置
  - 实体时间戳，比如在线状态的 `updatedAt`
  - 宿主版本：generation 加 sequence
- **合并方式**，选一种：
  - 单调：追加、取较大值、状态只前进
  - 后写为准

**一个条目只有一个版本域，不同版本域之间的数值一律不比较。** 同一样东西有两个来源时（比如在线状态：云端一份，本机宿主一份），就拆成两个条目，显示值从它们派生，并写明哪个优先。 后写为准的键如果拿不到读取的精确版本（服务端 head），推送就只用来让它失效，不直接改值。这样不会出现「读到 v12、被 v11 改回去」的回退。

**推送分四档。** 清点表（第 3 节）给每个模型标出档位。

| 档 | 来源 | 规则 |
|---|---|---|
| 日志 | 账号修订协调器：服务端按账号连续发号，`validatePage` 发现断号就整页拒收重拉，游标持久化 | 带完整值且版本更新 → 改副本；只说明「某个键变了」→ 失效。日志早于游标的部分被裁剪时（需后端确认是否会裁剪），整个账号的副本作废，从快照重建。 |
| 信号 | user bus 和广播，没有日志：置顶、额度、助理面板、连接、投递失败、身份移除等 | 收到信号就失效。订阅每次恢复（`onSubscribed`）、窗口回到前台时，这一档全部失效。 |
| 宿主 | 本机或远端机器的事件，版本域是宿主版本 | 规则和日志档相同，只在宿主版本域内比较。承认它是第二条推送通道，因为本机和离线会话没有账号修订。 |
| 无推送 | 公告、共同群等 | `fresh: 0`，打开即重读。 |

**不变量：**
- **I1 失效有凭据。** 失效时记下所需版本 r。只有版本不小于 r 的读数落地，或者在失效之后才发起的读取落地，才能清掉这条凭据。读取失败或被作废，就按退避重新排队，凭据一直保留。
- **I2 读取不早于推送，同键串行。** 读取在途中时到了推送或失效，这次读数不能清掉 I1 的凭据（等价于「再读一次」）。同一个键同一时刻至多一个在途读取：后发的读取取消先发的，或者接替它。这样两个戳相同的读数不会乱序落地。
- **I3 旧不盖新。** 落地的读数或推送，在同一版本域里比条目旧的就丢掉。单调合并的键按合并方式处理。
- **I4 写入是叠层。** 写入不改底值，而是在底值上叠一层，底值照常接收推送和读数。
  - **撤层**：写入返回了本版本域里的版本 → 底值追上这个版本时撤层。没返回版本 → 写成功时留一条 I1 凭据，要求一次在成功之后才发起的读取；凭据清掉时撤层。
  - **失败**：可撤销的写入直接撤层，不回滚到发起时抓的旧值，因为真值可能已经被别人改了。发件箱的写入留着叠层，继续重试。
  - 写入在发起时绑定账号。现有 `lib/stores/live/optimistic-model.ts` 的语义收进 replica。叠层这个原语在 PR 5 落进 `lib/replica.ts`；在此之前（PR 3），写入是点击时直接 `set`，被拒就重读，重读也失败就退回点击前读到的值，并告诉用户。
- **I5 快照条目重启后重读。** 只适用于走快照键的条目：从快照恢复的一律算旧值，挂载时先画出来，同时重读，因为快照不保存失效凭据。日志档里以 IM 库为持久层的条目（会话行、身份、名册）**豁免**：它们的版本戳和游标在同一个事务里落盘，待处理的修订也持久化（协调器的收件箱要等 listener 成功才删）。豁免的条件是：listener 必须等重读落地才算成功。因此每个模型各自注册一个 listener，不要把几个模型挂在同一个注册上，否则一个模型一直读不到，会连带拖住其他模型后面的修订。所以这类条目重启后直接可信，不会先闪一下。

**持久化：哪些条目可以 persist。上限要声明，写入时强制执行。**
- **能 persist 的模型必须在定义里写两个上限：**
  - `maxBytes`：单个条目序列化后的最大字节数。
  - `maxEntries`：这个模型在快照里最多保留几个键，超出时淘汰最旧的。
  - 写快照时任一项超限就不写这一条，控制台打 error（带模型名和大小），诊断计数加一。内存里的读数不受影响，下次启动这一条按「未知」重读。❌ 静默吞掉。
  - 上限写在模型定义里，审代码时直接看得到，测试也能直接验证。
- **快照块**（localStorage，一个账号一块 JSON，每次整块读写）的总量 = 各模型 `maxBytes × maxEntries` 之和，必须小于 64 KB 的预算。由一条测试把这个和算出来、守住。
- **名册、话题、会话行、身份、消息、成员和公告列表**：大小跟着数据走，给不出有意义的上限。它们不进快照，要么按条存进 IndexedDB（IM 库那一层，豁免 I5），要么不持久化。
- **现有的定法：**
  - `devices`、`sshMachineAddresses`：persist，每条 8 KB，`maxEntries: 1`。设备页是这次闪换最早的例子之一，不能退回去。超限就退回「未知」并报出来。
  - `devices` 的快照只存每台机器的卡片（`persist.kept`）：名字、种类、在线、版本这些第一帧要列的。随用量长的部分不进快照：动作清单（每个动作约 280 B，一台 Mac 登记几十个）、会话摘要（最多 `DEVICE_SESSION_DIGEST_LIMIT` 条）、项目。它们在恢复出来的行上缺席，读作「还没读到」，紧接着的那次重读补上。一张卡片约 0.6 KB，8 KB 放得下十来台机器。
  - 值的大小跟着账号的数据长、而第一帧只要其中一小部分的模型，用 `persist.kept` 只存那一部分；❌ 把整行塞进快照再调大 `maxBytes`。
  - `usageDays`、`creditDays`：不进快照。读数固定取最近 371 天（`HEATMAP_DAYS`），行数有上限，但一个活跃账号一年的行有几十 KB（`usageDays` 一天一个引擎一行，每行带 24 小时分布），单条就超过整块 64 KB 的预算；键里又带着当天日期，隔天就换键。首开画占位：热力图的占位是它自己的格子（53 周，版面与数据无关），不跳。

**写入只有两种，都是叠层（I4），区别只在失败时怎么办：**
- **可撤销**：设置、名字、开关。失败就撤层。
- **发件箱**：消息、读位、会话输入、附件。失败了留着重试。比如读位：在 mark_read 成功之前，「推到 50、未读清零」这一层一直盖在会话行的底值上，底值重读回来带着 unread_count=3，红点也不会复活（#1886 的形态）。
- 发件箱只有一个机制，带三条约束：
  - 幂等键：超时重试不会重复发送。
  - 每类各有合并策略：消息保序，读位只留最大值。
  - 绑定账号：上一个号的写入不会用下一个号的身份发出去。

**证明。** 前提：日志档里，服务端每次改动都给受影响的键记一条修订。修订连续、按账号排序，并且和数据改动在同一个事务里提交。读取走主库，所以「失效之后才发起的读取」一定能看到这次改动。

1. 协调器保证每个订阅者内部按修订顺序处理；订阅者之间并行，彼此的先后不作保证，顺序靠 I3 在合并时守住。
2. 所以每条修订要么以更新的版本改掉条目，要么通过 I1 留下凭据。
3. 凭据只会被「足够新」的读数清掉（I1、I2），读取失败会重排。
4. 写入不改底值（I4），不会把推送盖住。
5. 所以条目最终收敛到不早于最后一条修订的值，不会停在更旧的值上。
6. 信号档没有这个保证：它只保证「最后一次恢复连接之后的变化不丢」。这是它和日志档的区别，写在清点表里。

## 4. 名字

改成 **replica**，代码里写 `replica({ … })`、`useReplica`、`Reading`。原因：readModel 在 CQRS 里指服务端查询侧的投影，容易让人误解；replica 直接说的是「真值在别处，这里是带新鲜度的一份副本」。

代价是一个机械提交：44 个定义、约 46 个调用点、测试和检查脚本里的文案，由类型检查兜底（PR 2 的第一个提交）。

**唯一例外**是快照的存储键 `gugu.readModel.v1`，不改。改了等于丢掉所有人的快照。

## 5. 业界对照

**结论：经典解法只有一句话，就是在内存里放一份能同步读的缓存，在第一帧之前把上次的值灌进去。** 查过的每个库都是这个结构，没有比它更「一步到位」的。replica 就是这个解法：缓存、去重、失效和后台重读都交给 TanStack 的 `QueryClient`，手写的只有三块——快照读写、账号生命周期、不带默认值的三态读数。

首帧的值只有两种来法：

| 做法 | 机制 | 谁在用 |
|---|---|---|
| A 同步灌入 | 应用代码执行之前，值已经放在能同步读的地方 | SSR 的预载状态；TanStack `hydrate()`；Apollo `persistCacheSync`；我们的 localStorage 快照 |
| B 拦住首帧 | 存储是异步的，读完之后才画第一帧 | Apollo `await persistCache`、TinyBase、VS Code、Linear；我们的 `appSettings.getAll` 和 `viewState.getAll` |

| 方案 | 首帧 | 为什么不选 |
|---|---|---|
| TanStack `PersistQueryClientProvider` | 在 `useEffect` 里才灌回，首帧必然是空的 | 正好退回到我们要消掉的现象 |
| TanStack `persistQueryClientRestore` | `await` 之后才灌，中间隔着微任务 | 能省的手写代码不到 40 行，而 `maxBytes` / `maxEntries` 官方都没有，还得自己写；不传 `retry` 时写满配额会静默失败 |
| Relay：归一化存储加 subscription | 只在内存里，不跨重启持久化 | 需要 GraphQL 和全局 id，归一化要改后端协议 |
| Replicache、Zero、Linear、Electric、PowerSync、RxDB | 都是异步存储：要么先返回未知，要么拦住首帧 | 它们解决的是整库同步、离线写和冲突合并。账号数据不能整体下载，服务端还要按 RLS 做投影；在首帧这件事上，它们并不比我们强 |
| 主进程 SQLite 加 preload 同步注入 | 对真值在主进程的数据来说很自然，现在已经这样做了（系统语言、app 设置、视图状态） | 账号数据的真值不在主进程；网页和手机两个壳没有主进程，手机上也没有同步的 IPC。localStorage 是三个壳上唯一都能同步读的存储，Chromium 第一次访问时会一次性同步取回整个 origin 的键值 |

**选择：** TanStack 式的按键副本，推送和顺序用 Linear 式的修订日志。归一化只做到「一个实体一个键」；消息这类流形状交给存储引擎处理。只有两种情况才需要换快照背后的存储：快照超出预算，或者手机上 WebView 回收 localStorage 在真机上造成了可见的问题。到那时只换快照读写那两个函数，模型定义和界面都不用改。

## 6. 订阅原语

**只留一个：`useSelect(source, select, equals)`**（`lib/selectStore.ts`，见 #2689）。理由：几种订阅写法的差别只在数据从哪来，不在怎么订阅。只有一个原语，才能统一保证两件事：同一轮渲染读到的是同一份值；只有自己那一片变了才重渲。

- **按 id 选一片**：replica 本身就是一个键一份读数，`useReplica(model, [id])` 订阅的就是那一片。在整份 store 里按 id 取：`select: v => v.byId[id]`。
- **相等由调用方定**：`equals` 默认浅比较，可以传 `isDeepEqual` 或自定义比较。
- **适配层**：replica 和 MobX 各自提供一个 `Readable`（`get` / `subscribe`）。`get` 必须返回缓存好的稳定引用：replica 返回读数对象本身；MobX 用 `computed` 加比较器缓存，否则每次渲染都会得到新对象，陷入死循环。

**迁移：**
- react-query 的 `useQuery` 和 `select` 不再出现在组件里（`select` 目前一处都没用）。
- MobX 的 `observer`（180 个文件里约 294 处）：每个域的 PR 删掉本域的 MobX。在 PR 5（会话域）删掉最后一个 MobX store 和适配层，这就是终点。
- 源码检查（`scripts/checks/effect-fetch-state.mts`，在 `lint:source` 里，PR 3 起是硬规则，没有 baseline）：effect 不许把读到的东西塞进组件 state；读数不许回退成字面量；`lib/replica.ts` 以外不许直接用 react-query 的读和取数状态 hook（`useQuery`、`useQueries`、`useInfiniteQuery`、`useSuspenseQuery`、`useIsFetching`、`useQueryClient`），也不许调用 `queryClient` 的方法（写入仍可用 `useMutation`）。`observer(`、`useSyncExternalStore` 的棘轮随 PR 4、PR 5 各域一起做。
